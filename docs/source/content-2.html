Chapter 3: System Design Document (SDD)

3.1 Introduction

3.1.1 Purpose of the System

The purpose of WoredaCare is to let citizens reserve in-person woreda services online and to let the woreda departments serve those reservations in an orderly, transparent and auditable way. This chapter describes how the system is decomposed, deployed and secured, and how its data is stored.

3.1.2 Design Goals

GoalHow the design achieves it
SecurityServer-side authorization for every request (CASL abilities with department, service and ownership conditions), hashed passwords, HttpOnly session cookie with CSRF protection, input validation, rate limiting and security headers.
Data integrityDatabase constraints, transactions, PostgreSQL advisory locks for bookings and queue tokens, and conditional status updates so that concurrent actions cannot corrupt the state.
ResponsivenessA WebSocket channel pushes change notices so that open pages refresh within about a second.
MaintainabilityA strict layered API (routes, middleware, controllers, services, repositories), small single-purpose modules, one response envelope and versioned schema migrations.
AccountabilityAn append-only audit log with actor, time and before and after snapshots of every appointment decision.
Usability and reachA browser-based client that works on desktop and mobile widths, with plain-language messages and live status.
Correct local timeAll scheduling uses woreda time (Africa/Addis_Ababa), independent of the device time zone.

3.2 Current Software Architecture

There is no current software system for booking or queue management at the woreda; the existing process is manual (Section 2.2). Therefore no existing architecture constrains the design, and no data migration from a previous system is required.

3.3 Proposed Software Architecture

3.3.1 System Design

1. Overview

WoredaCare uses a three-tier client-server architecture (Figure 3.1). The client tier is a React single-page application served as static files and run in the user's browser. The application tier is a single Node.js process running an Express REST API under /api/v1 and a WebSocket hub under /api/v1/ws. The data tier is a PostgreSQL database. The client sends HTTPS requests to the API and receives change notices over the WebSocket; after a notice it re-reads the data it displays.

Inside the API every request passes through the same ordered layers (Figure 3.2): routes map the URL to a handler; middleware assigns a request identifier, logs the request, applies CORS and rate limits, authenticates the JWT, checks CSRF, checks the CASL ability and validates the input; controllers translate between HTTP and services; services implement the business rules; repositories run parameterized SQL.

4. Persistent Data Management

Persistent data is stored in a PostgreSQL relational database. The schema is created and changed only through 21 versioned migrations managed by node-pg-migrate; every migration has a reversible down step. A seed creates the first administrator. The final schema consists of 13 tables (Figure 3.5); the full data dictionary is given in Appendix B.

TableContent
departmentsWoreda departments with unique code, room and contact phone

usersCitizens, officers and administrators with role and, for officers, department

Integrity mechanisms. Primary, unique and check constraints protect the data (for example unique department and service codes, positive capacities and allowed status values). Foreign keys use explicit delete rules (RESTRICT, CASCADE or SET NULL). Bookings and token issuing run inside transactions with PostgreSQL advisory locks, and status changes use conditional updates. Dates are stored as DATE values in woreda time.

Design notes. Audit entries deliberately copy names and dates instead of referencing other tables, so that history is preserved when records change. Two weaknesses are documented for future work: officer service assignments are stored as JSON in the users.address column instead of a separate table, and appointments.citizen_id has no foreign key to users.

6. Access Control and Security

Access control is role-based with attribute conditions. On every request the JWT middleware identifies the caller and builds a CASL ability from the role, department and assigned services; route middleware then checks the required action, and services re-check the conditions against the actual record (for example that an appointment belongs to the officer's department and services, or to the citizen). Security mechanisms.

  • Authentication: passwords are hashed with bcrypt; a signed JWT (HS256) carrying the user identifier, role, department and services is stored in an HttpOnly cookie; a Bearer token is accepted for API clients. Signing out records the token identifier as revoked. Sessions do not expire on inactivity by design.
  • Brute-force protection: five failed sign-ins lock the phone or email for 15 minutes; requests are rate-limited per IP address.
  • CSRF protection: a double-submit token (cookie plus X-CSRF-Token header) and an Origin check are required for state-changing requests that use the session cookie.
  • Input handling: every body and query is validated with Zod; SQL is always parameterized; request bodies are limited to 1 MB; Helmet sets security headers; CORS allows only the configured web origins.
  • Data exposure: public tracking and availability responses contain no personal contact data; appointment slips are restricted to the owner, the responsible officer and the administrator.

4.1.2 Interface Documentation Guidelines

  • Module headers: every file starts with a comment stating its responsibility; public functions carry a JSDoc comment describing parameters and results.
  • Naming: service factories are named createXService, controller factories createXController and route factories createXRoutes; repository functions use findX, countX, create, update and remove. File names follow name.layer.js (for example queue.service.js).
  • Data names: JavaScript and JSON use camelCase; database columns use snake_case; models translate rows with fromRow.
  • REST interface: resources are plural nouns under /api/v1; actions that are not plain updates use sub-resources (for example POST /appointments/:id/cancel).
  • Response envelope: success responses are { success: true, message, data, meta }; errors are { success: false, message, error: { code, details }, meta }.
  • Status codes: 200/201 success; 401 not signed in; 403 not allowed; 404 not found; 409 conflict with the current state (slot taken, capacity reached, already decided); 422 validation failure with field details; 429 too many attempts.

5.2 System Implementation and Prototype

The prototype consists of approximately 17,800 lines of client code and 9,000 lines of server code (JavaScript and JSX, excluding dependencies). The following implementation details are central to the system's behaviour:

  • Concurrency-safe booking: a booking takes a PostgreSQL advisory lock on the service and day inside a transaction before counting the taken places, so simultaneous requests for the same slot cannot both succeed.
  • Day rules: one function resolves a day from the base schedule and the calendar exceptions, so booking, availability and the booking form apply the same rules.
  • Live updates: services publish domain events; the realtime hub broadcasts typed notices (appointments, catalog, staff, citizens, audit) over a single WebSocket per page, which reconnects with backoff.
  • Countdowns: the client learns the server clock from every API response, so countdowns are correct even on a device with a wrong clock.
  • Audit trail: every appointment event is written once with before and after snapshots and paged with a keyset cursor.

5.2.3 Usability Testing

Formal usability testing with representative citizens, department officers and administrators has not yet been conducted. During development the interface was checked for phone and desktop widths, readable labels and messages, accessible timer text and keyboard use, but these checks do not replace testing with real users. The planned procedure is:

  1. Recruit participants from each user group [number of participants to be decided by the team].
  2. Ask each participant to complete typical tasks: register and book an appointment, find their queue position, cancel an appointment (citizens); approve, check in, call and complete (officers); add a holiday and review the audit log (administrator).
  3. Measure task completion, time on task and errors, and collect the System Usability Scale (SUS) questionnaire [9].

Chapter 6: Conclusions and Recommendations

6.1 Conclusions

The project produced a working web-based system that moves the booking of woreda public services online while keeping the service itself at the desk. Citizens can register, book appointments under enforced schedule rules, follow their status and queue position live and cancel within the allowed time. Department officers decide requests and run the desk queue for their own department and services, and the administrator manages accounts, catalog, schedules, calendar exceptions and an auditable record of every decision.

The design emphasizes server-side enforcement of all rules, concurrency-safe booking, an append-only audit trail and live updates. The system was verified with 75 automated tests, 146 end-to-end API checks and fifteen browser scenarios, all passing in the final run. The main limitations are the absence of SMS integration and of per-department operating hours, together with the partially implemented features listed in Table 2.5.

6.2 Recommendations

  1. SMS integration: connect an SMS gateway for booking confirmations, approvals, reminders and turn notifications.
  2. Per-department operating hours: allow one working schedule per department, as required by the schedule management specification.
  3. Calendar view: add the monthly and weekly calendar page using the existing calendar API, and give department heads read-only access to their schedule.
  4. Public tracking: connect the Track page to the existing tracking API so that visitors can check a booking without signing in.
  5. Settings: enforce the auto-approve and advance-booking-days settings, or remove them from the settings form.
  6. Check-in rule: allow check-in only on the appointment date.
  7. Data model: store officer service assignments in a dedicated table and add a foreign key from appointments to users.
  8. CSV export: neutralize values beginning with =, +, - or @ to prevent spreadsheet formula injection.
  9. Interface: add menu entries for the existing reports, settings, profile and notification pages, fit the officer appointment table to standard screen widths, and consider an Amharic language option.
  10. Operations: prepare a production deployment (HTTPS, process supervision, database backups) and carry out the usability study described in Section 5.2.3.
